Getting started

Analytics lets you design complete analytics dashboards visually — no hand-coding required. Open a browser, choose a data source, drop it onto the canvas, and export a production-ready file in minutes.

The first time you sign in, a welcome screen greets you (by name, if you're signed in as a real user) and offers a choice: Take a quick tour (a short step-by-step carousel) or Take the guided tour (a spotlighted walkthrough of the real app), plus three quick-action shortcuts — Explore data, Build a dashboard, Bring your data — that jump straight to that section if you'd rather skip the tour entirely. It only shows itself once; revisit it anytime from Settings → Tour or the ⋯ menu's Tour item.

The left rail switches between the app's sections: Home (quick-create + your recent/pinned dashboards, plus a small rotating tip card — click its → arrow to see another), Repository (every data source and dashboard you have, browsable and searchable from one page — type in its search box to filter both lists at once; a dashboard also matches if the query doesn't hit its title but does hit one of its bound data access's column names (the card then shows exactly which column matched), so a schema change in a data source is one search away from finding every dashboard it could affect; a Group filter chip strip above the data-source grid lets you narrow to one group at a time (the same "Group" field every data source carries); click a data source to jump straight to it in the Studio library, or click a dashboard to reopen it; hover a data-source card to reveal ✎ edit / 🗑 delete actions — the same data-source builder and delete used by the Studio library, so both views always agree), Studio (the builder described below — visible to developer and admin accounts only; a viewer account never sees this rail item, and opens dashboards through the read-only viewer route instead, described just below), Settings (app-wide preferences), and — for admin accounts only — Admin (manage who can sign in to this workspace and whether they're an admin, a developer, or a viewer — a developer gets everything a viewer does plus Studio access; admin is a superset of developer). Collapse the rail to icons-only with the toggle at its bottom. Your browser's Back/Forward buttons step through the sections you've visited instead of leaving the app; Back also closes an open editor, panel zoom, or slideshow first, before it steps back through sections — and in Explore, Back (or its own "Back to datasets" button) returns you from an open dataset or saved analysis to the dataset picker without leaving the Explore section.

The top bar stays put across every section. On the left it names the section you're in; in the center is a Search box (or press ⌘K / Ctrl-K anywhere) that opens the command palette to jump to any command, dataset, or dashboard. On the right sit quick actions: What's new (the release feed, with a dot when there's something unread), What's next (a peek at the near-term roadmap), a one-click dark-mode toggle, the fleet app switcher, and New. On phones the bar keeps the essentials — the section name, search, the app switcher and New — with the rest tucked into the rail drawer and the ⋯ menu.

Quick import: Home's Quick import card is the fastest way in with your own data — drop a .csv or .json file straight onto the card (or click it to browse), and it's parsed, profiled column-by-column (recognizing map fields, dates, measures, and categories from the column names and values), saved as a real dataset, and used to auto-build a real dashboard — a headline KPI plus whatever mix of bar, donut, line, and table Views the data actually supports (a time View only appears with a real date column; a category View is capped to its top values instead of one bar per row) — opened right in Studio so you can start refining immediately. No connection setup needed — a "Quick imports" file connection is created for you the first time. Files stay under 2MB and inline (works fully offline); host a bigger file elsewhere and use the DuckDB (remote file) connector instead. A Quick import creativity setting (Settings → Dashboard defaults, Low by default) controls how adventurous the auto-build gets: High mixes in a map, a treemap, a slope chart, and an ensemble view on top of the same conservative base — but only the ones your data actually supports (a map needs a real geo column, a slope chart needs a genuine before/after measure pair, an ensemble needs a real multi-provider series column). A small Low/High tuner appears under the dashboard title right after a Quick import, letting you flip creativity and watch the dashboard rebuild in place from the same file, no re-upload needed. A quick-built dashboard isn't saved to Dashboards until you click Save — an "Unsaved — Save to keep" reminder shows next to the tuner until you do, and opening a different dashboard first warns you instead of silently discarding it. The same drop-a-file affordance also lives right on Studio's empty canvas — "Canvas is empty" offers an Import a file button alongside Open data panel / Add a text View, and you can drop a .csv/.json straight onto the empty canvas too.

Export/Import repository: the Dashboards page's "Export dashboards…" button opens a picker so you can choose which dashboards to export (it defaults to all selected — use Select all / Clear to narrow it). The download is a single JSON file with the chosen dashboards plus the data sources you authored that they use (via ＋ New source — the bundled catalog ships with the app, so it's not duplicated into the export) and the relevant pins + workbooks; export everything and you get your whole local inventory, exactly as before. "Import repository…" merges a previously exported file back in — it's additive, so importing never deletes anything already here; a data source with the same id is overwritten by the imported version, and dashboards merge by id (keeping the newer of any duplicate). Handy for moving your work to another browser/device, or as a manual backup.

Workbooks: file your dashboards into named collections on the Repository page — type a name next to "+ Workbook" to create one, then click the chip strip above the Dashboards grid to filter to just that workbook (or "Unfiled" for anything not yet organized). Each dashboard card gets its own "Workbook" dropdown to assign or move it. Hover a workbook's chip for a ✎ rename button (swaps the name into an editable field — Enter saves, Escape cancels) alongside the ✕ delete. Deleting a workbook never deletes the dashboards inside it — they just become unfiled again. Once you have at least one workbook, the same filter chip strip (without the add/rename/delete controls) also appears on the Home page above Pinned/Recent dashboards, for a quick glance without visiting Repository. If any installed sample pack has contributed dashboards, a "Sample packs" chip joins the strip too, filtering to just those — Home's "Browse examples" card jumps straight here with that chip pre-selected, instead of opening a separate examples picker.

Select multiple / bulk delete: click Select on the Dashboards page to enter multi-select mode — a checkbox appears on every tile/row, and tapping anywhere on a card or row toggles its selection instead of opening it. A bar above the list shows how many are selected with Select all / Clear and a Delete button that removes every selected dashboard after a confirmation (this can't be undone). Sample-pack dashboards can be selected and deleted individually like any other — removing one just drops it from your workspace; remove and re-add the sample pack in Settings to restore the full set. Click Select again (now labeled Cancel) to leave select mode.

Compare dashboards: the Repository page's "Compare dashboards…" button opens a picker for any two of your saved dashboards — a live preview of each renders side by side (the same render every export/preview uses, so it's a genuine "which of these looks better" comparison, not a thumbnail), with a plain-English summary of what differs between them underneath. This is distinct from a dashboard's own Version history (below), which only ever compares a dashboard against its own past checkpoint — Compare dashboards is for two different saved dashboards, e.g. judging two drafts against each other.

"Changes since you were last here": a recent-dashboard card on Home or Repository shows a small "N changes since you were last here" note whenever the dashboard has moved on since the last time you actually opened it — added a View, changed the accent color, whatever Version history's own plain-English diff would say. Hover the note for the actual list of changes. It clears the moment you reopen the dashboard (that becomes the new "last here"), so it only ever nudges you toward what's new since your last visit, not a running history.

Install it: the Studio is an installable, offline-capable app — most browsers offer "Add to Home Screen"/"Install app" from the address bar. Home — instant analytics

Home greets you with your content, live. Click the small house button on any dashboard card (Home or the Dashboards section) to feature it: featured dashboards render on Home as real, scaled-down live previews — the actual dashboard engine in a view-only frame, not a static thumbnail — and one click opens them in the Studio. The most-recently-featured dashboard gets top billing as a full-width hero card; the rest sit in a grid below it. Analyses pinned in Explore (★) render the same way as live chart Views that open back in Explore. Datasets and connections you've pinned to the top of their own catalogs (the same ★ toggle on each row) show up too, as compact cards under Favorite datasets & connections — click one to jump straight into its editor. The frames follow your light/dark theme and hydrate lazily, so offscreen cards cost nothing. In Simple mode the app boots to Home whenever you have featured content, and to Explore when you don't; your own last-used section always wins. The Featured, Pinned analyses, Favorites, Examples and Dashboards sections each carry a small ▲▼ control in their heading — reorder them to put what matters most to you at the top; the order is saved and sticks between visits.

Every dashboard card or row (on Home or in the Dashboards section) also carries a small eye icon, Open in viewer — it opens the dashboard read-only, full-page, in a new tab: the same live, interactive renderer (filters, cross-filter, provider toggles all work), with none of the builder chrome and no way to change the original. Handy for sharing a link to someone who should read a dashboard, not edit it. A private dashboard's viewer link only works for its owner (or an admin) — same rule as everywhere else it's private. A viewer account clicking a dashboard card or row lands here directly (Studio isn't open to them at all — see above); the viewer page's top bar offers Save a copy to everyone, viewers included — it forks the dashboard's saved configuration into a brand-new dashboard you own, without touching the original, so you can make it your own starting point. A developer or admin viewing the same page additionally gets an Edit in Studio button that jumps straight into the builder, editing that exact dashboard.

The viewer's top bar also has an Export button (available to everyone) with the same formats Studio offers: Dashboard (.html) — a self-contained file you can drop on any static host or open offline — PDF (print), and the editable spec (.json). A sample or demo dashboard exports with its data baked in, so the download is complete on its own; a dashboard backed by a real data source keeps querying that source live, in the viewer and in the exported file alike.

Explore — dataset-first analyses

Explore (left rail) is the fastest path from data to chart, built for non-experts: pick a dataset on the left (your workspace datasets first, sample data below them), see its rows as a table, choose a chart, and adjust the column mapping — the live preview underneath is the real dashboard renderer, so what you see is exactly what a dashboard will show. Give it a name and Save analysis.

  • Analyses are reusable. Saved analyses appear in the left list here, in the Studio library under Views (click + Add to dashboard or drag one onto the canvas), and — when pinned with the ★ — as cards on Home.
  • Adding a result to a dashboard is unambiguous. The result panel's + New dashboard button drops your chart into a brand-new dashboard; Existing dashboard… opens a picker of your saved dashboards and adds it to whichever one you choose. Either way it's saved as an analysis first if you haven't already.
  • Self-contained. An analysis embeds its data access, so it keeps working (with sample rows) even if the original workspace dataset is later deleted.
  • Every scale of chart. The chart chips include the everyday types plus the US choropleth map (county / state / USDA district / watershed / congressional district / ZIP code) and the Ensemble common-estimate chart with its reference-series option. A map's Renderer picker (Built-in vs Interactive GL — pan & zoom at any polygon count) is right there too, and the choice is saved with the analysis. On the Interactive GL renderer, a Zoom/pan controls option shrinks the on-map cluster to a compact size or hides it entirely (Show / Compact / Hidden) — handy when the controls compete with a dense dashboard layout; dragging and scroll-to-zoom keep working even when the cluster is hidden. A Controls position option docks that same cluster in any corner of the map (top right by default, matching every map saved before this option existed).
  • Workspace datasets run live for the table preview and the chart; if a live run fails, Explore falls back to typed sample rows and says so.
  • Rollups (group-by aggregation). Under the column mapping, the Rollup control lets you aggregate the value column with Sum, Mean, Median, Min, Max or Count, grouped by one or two dimensions (Group by / Then by) — so a detail dataset becomes a chart of totals or averages without building a Job first. The rollup is saved onto the analysis, so it re-aggregates the same way on Home, in any dashboard, and in the exported HTML. (Geo and Ensemble charts carry their own aggregation, so the control is hidden for those.)
  • In Simple mode, Explore is the default section on first open.
  • New dataset without leaving Explore. The + New button next to the dataset search opens the same dataset editor the Datasets section uses — save it and Explore selects it immediately, ready to chart.

Sample packs

Sample packs (Settings, and the Studio library's left View) are ready-made demo content you can install or remove. A pack can add dashboards, datasets, connections and jobs — all with synthetic (made-up) sample data, never your real data — and Remove takes back exactly what Install added. Like the built-in catalog, sample packs live under the same Sample content switch in Settings — turn that off and both disappear from the library, with nothing deleted.

  • Conservation Insight is an illustrative sample for a county-level cover-crop and conservation-tillage ensemble use case: a raw provider CSV to try a mapping workflow on, four pinned Ensemble analyses (one per practice), and a featured multi-View dashboard pairing them with a county choropleth — all live on Home the moment you install it. All of its data is synthetic and labeled as illustrative. The featured dashboard also demonstrates two different filtering styles: a plain filter bar (Practice, Since year) that narrows individual Views, and a linked cross-filter — click a provider on any adoption-trend chart's legend and every choropleth on the dashboard re-colors together. Installing it also adds eight extra showcase dashboards (a practice-adoption scorecard, a crop/practice flow view, a watershed-scale adoption view, a program cost-share ROI view, a provider-agreement-over-time view, a county-level outlier-detection view, a year-over-year practice-switching view, and a richtext-led narrative overview rolling all of it up, each with their own filter bar too, save the overview) to both your Dashboards screen and the Examples ▾ gallery — removing the pack takes all nine dashboards back out again, so the workspace doesn't get cluttered for everyone else.
  • Data Management & Governance is the built-in generic showcase gallery (Data Governance, Data Platform Operations, Product Delivery, Finance, Marketing, Incident Response, Compliance, and the Interactive Feature Tour) folded into a toggleable pack, installed by default so the gallery looks exactly as it always has. Unlike Conservation Insight, this pack adds no connections, datasets, or jobs — Install/Remove shows or hides those eight gallery entries and adds or removes them from your Dashboards screen, so turning it off just declutters both for a pitch that wants to stay focused on Conservation Insight alone.

Jobs — prep & rollup

Jobs (left rail) prep one dataset before it's charted: rename or cast a column, derive a new one from arithmetic on two others, filter rows, roll everything up with a group-by aggregate, and join or union in a second dataset. Run a job and the result is saved back as an ordinary dataset — ready for Explore, the Studio library, or any dashboard — and re-running the same job updates that dataset in place, so an annual data refresh is a single click.

  • Steps run in order and can be reordered or removed; Preview runs the source dataset live and shows the pipeline's output before you save.
  • A source field list sits above the steps, showing every column on the source dataset with a best-effort type icon and color (Numeric/Date/String, guessed from the column name) — see what's available before you start picking columns.
  • Sample rows and an output preview sit below the field list: a small live sample of the source dataset's real rows, and an approximate preview of what the output looks like after the current steps run — both update instantly as you edit steps, no Preview click needed. Join/union steps only know the linked dataset's column names here, so their preview rows are honestly approximate; click Preview for the authoritative result.
  • Column fields are dropdowns — group-by, rollup-metric, and join/union key columns are picked from each dataset's real, known columns rather than typed by hand. A dataset that hasn't been queried yet is probed live in the background the moment you open the job editor, and the dropdowns fill in as soon as its columns are known.
  • A small diagram under each rollup, join, or stack (union) step shows the operation visually — columns going in, the operation in the middle (group-by columns for a rollup, the join key/type for a join, the other dataset for a stack), and the columns that come out — so the shape of what you're building is visible at a glance, not just the raw fields.
  • Multiple rollup levels — add a second (or third) aggregate step to roll up an already-aggregated result again (e.g. sum acres by county+year, then average that across years for a county-only figure); each aggregate step's group-by/metric dropdowns show the columns as they exist at that point in the pipeline (the previous step's output), not the original source dataset's columns.
  • Rollup metrics include sum, average, count, median, and a weighted mean — the honest way to aggregate a percent metric from county up to State, USDA Crop Reporting District, or HUC8 watershed: a flat average of percentages misrepresents counties of very different size, so pick an acreage (or similar) column as the weight.
  • Join adds a second dataset's columns onto matching rows by a key column (inner drops unmatched rows, left keeps them with blanks); added columns that collide with an existing name get an auto suffix, or set a prefix yourself.
  • Union stacks a second dataset's rows onto the pipeline's existing schema — the normalize-and-stack case for combining several differently-shaped sources (e.g. five providers with five different raw column names) into one common table. Each output column maps from a column in the other dataset (or falls back to a same-name match, else blank).
  • Add unique row ID stamps a stable, unique id onto every row currently in the pipeline — place it after a join, union, or aggregate step to key the rows at their final grain (an aggregate collapses many source rows into fewer output rows, so an id added before it wouldn't match the shape you actually save).
  • Custom SQL runs an arbitrary query against the pipeline's rows so far (table t), via an in-browser DuckDB engine loaded the first time a job uses it — useful for anything the built-in steps don't cover directly.
  • Refresh reminder (weekly/monthly/quarterly/yearly, optional) flags a job ⏰ Refresh due on the Jobs list once it's overdue against its last run — a hint, not real scheduling (there's no server to run a cron; the app is static and client-side), so it only shows up next time the list is open. Handy for the annual-refresh case: set it once and the list tells you when it's time to click Run again.

The builder

The workspace is divided into three resizable panes. Each pane can be collapsed to a labeled rail by clicking the ‹ / › collapse button.

Polecat apps switcher: the app bar (top of the screen, next to ＋ New) carries a waffle (3×3 grid) button that opens the Polecat suite switcher — one-click jumps to the other apps in the family (Chat, JobTracker, AutoSelector, Relay, Games, Manager, and this one, highlighted as the current app). It's the same switcher every polecat.live app carries, themed to whichever Studio look you're using.

What's new: the Changelog button in the footer opens the full release feed in a right-hand panel — every version, newest first, with live search (matches highlighted) and Central-time stamps. A small dot on the button means there are releases you haven't seen yet; opening the panel clears it. Close with the ✕, Escape, or a click on the backdrop.

Three panes

  • Query Library (left) — All data accesses organized by group. Search by name, table, or column keyword. Drag any card onto the canvas to create a View. In Advanced mode, use ＋ New source to author your own query.
  • Live preview (center) — The real dashboard rendered in an iframe. This is byte-identical to what the export produces — no approximation. Click a View to select it; drag the title bar to reorder; drag the right edge to resize.
  • Inspector (right) — Contextual editor for whatever is selected. When nothing is selected, shows the dashboard-level controls. Click a View → View inspector. Click a KPI tile → KPI inspector. Click a filter → filter inspector. Click the title banner itself → Header inspector.

The View inspector is context-aware: interaction sections like Drill-through, Detail drawer, Cross-filter, Conditional formatting, and Color scale only appear when the selected chart type actually supports them (e.g. Conditional formatting shows for Bar/Donut/Treemap/Lollipop but not for Table or Line — clicking a table row instead opens the Detail drawer). This keeps the inspector focused on settings that do something for the current chart.

Renaming a dashboard: the dashboard title in the toolbar above the live preview renames in place — click it and it becomes a text field (Enter or clicking away commits, Escape cancels). The Dashboard inspector's Title field is the same value, edit whichever is closer. The Title (the display name shown in the dashboard's header/banner) and the File name (stem) (the lowercase-with-dashes name used for exported files, e.g. my-dashboard.html) are two independent fields right below it, so you can rename either without the other changing.

Header logo: the Dashboard inspector's Header logo field (below Subtitle) uploads a PNG/JPG/SVG (up to 200KB) that replaces the default "P" mark in the dashboard's banner, in both the live preview and the exported Dashboard Framework — a per-dashboard brand mark, separate from the app-wide rail branding in Admin. Leave it blank to keep the default mark.

Header link: the Header link URL field right below it makes the logo + title in the banner clickable, opening that URL in a new tab — handy for linking back to a company site or portal. Leave it blank to keep the banner as plain, non-clickable text.

Show dashboard header (embed mode): the Header toggle in the Dashboard inspector. Turn it off and the entire title banner and description bar disappear from both the live preview and the exported .html, leaving just the KPIs and Views — a clean, chrome-free dashboard you can drop straight inside your own page. Turn it back on and the title, subtitle and description return, all still editable in the inspector.

The header as an object: click anywhere on the title banner in the live preview (not on one of its buttons) to select it, the same way clicking a View or KPI tile does — the Inspector switches to a dedicated Header view with quick Title/Subtitle fields and a ✕ button that hides the whole banner (the same effect as the Show dashboard header toggle above). Double-clicking the title or subtitle text directly still edits it in place without needing to select first. Logo, link, and light/dark stay on the Dashboard panel (click "‹ Dashboard" at the top of the Inspector to get back there).

Title size: right below Subtitle, the Title size picker (Default / Small / Large / Extra large) resizes just the banner title text — handy for a dense multi-KPI ops board (Small) or a single-hero exec dashboard where the title should dominate the banner (Extra large). Leave it at Default to keep the standard weight/size.

Subtitle style: next to Title size, the Subtitle style picker (Normal / Italic / Bold / Bold italic) adds emphasis to just the banner subtitle — e.g. Italic for a light tagline, Bold for a subtitle that should read almost as loudly as the title.

Card style: below Subtitle style, the Card style picker chooses the render mood for every chart card and KPI tile on the dashboard. Raised (default) keeps the standard shadow, glass-edge highlight, and hover lift. Flat / minimal strips all three for a quieter, editorial look — same data and layout, just a calmer surface treatment for a boardroom setting. Sketch / hand-drawn swaps the shadow for a dashed border and a wobbled, asymmetric radius for a whimsical, hand-drawn mood.

Share this dashboard: further down the Dashboard inspector, Copy shareable link encodes the whole working dashboard (Views, KPIs, filters, style — everything) into a #share=… link with no file attachment and no server involved. Opening that link (in any browser, on any device) reopens the exact same dashboard directly in the Studio builder — handy for handing a work-in-progress to a teammate. This is different from the Shareable link section above it (only shown when the dashboard has filters), which copies a short #filterId=value hash meant for an exported Dashboard Framework file, not the builder itself. Once you've sent a full link once and keep editing, a second button — Share just my changes — appears: it copies a much shorter link carrying only what changed since your last full or update link. It only works for a recipient who already has this dashboard (from opening a previous link for it) — opening it without that base first shows a clear error instead of silently failing.

Version history: right below Share this dashboard, every time you hit Save (the topbar's Save button or Ctrl/⌘+S — it saves to your Dashboards catalog) a timestamped checkpoint of the whole dashboard is kept here — up to the last 10 per dashboard. Click any entry to restore it: your current unsaved changes are replaced with that checkpoint (after a confirm), and the restore itself becomes a new checkpoint, so a restore can always be undone too. This is separate from in-session Undo/Redo (lost on reload) and from the single unsaved-draft autosave — it's a real "time travel" timeline, kept locally on this device only. Each entry also has a ⇄ Compare to current button that opens a plain-English change list (title/style fields, and which Views/KPIs/filters were added, removed, or changed) between that checkpoint and the dashboard as it stands now — so you can see what a restore would actually undo before committing to it.

Dashboard theme: at the top of the style section, above Accent color, the Dashboard theme picker swaps the WHOLE look of the preview and exported dashboard in one click — background, View, text, brand, and all ten chart series colors — rather than tweaking one piece at a time. Polecat is the warm terracotta/plum house look and the default for new dashboards (its ten-color series ramp is WCAG-AA and colorblind-safe on both its cream light surface and plum-black dark surface); Classic Blue is the original look (unchanged); Fleet Modern applies a cooler, WCAG-AA-contrast, colorblind-safe dark/light system aligned with the rest of the Polecat fleet (kills the old flat-blue cast in favor of a proper background/View/text hierarchy and a validated 10-color series palette); High Contrast pushes further still — true black/white extremes with solid (not soft-tinted) borders and its own validated series palette, for maximum legibility; Editorial is a warm, paper-and-ink boardroom mood (cream background, warm ink text, an earthy-but-saturated series palette) for a quieter, more "print report" feel; Neon is a synthwave/cyberpunk mood — near-black Views with electric cyan/magenta brand accents and its own validated series palette, and keeps the banner/header near-black in both light and dark mode for a consistent "neon on black" identity; Custom lets you author your own — pick Background, View, Text, and Brand colors for light and dark mode (8 fields total) and everything else (borders, subtle fills, sidebar, secondary accent, grid lines) is derived automatically using the same relationships the curated presets use, with a live warning if your text/background pick falls below the WCAG AA 4.5:1 contrast minimum. A custom theme travels with the dashboard like any other setting — Save, Export, and Share this dashboard all carry it. Below the color editor, Theme presets lets you save the current custom theme under a name and apply (or delete) it later — handy for reusing the same house colors across multiple dashboards instead of re-picking all 8 fields each time. Accent color, Header background color, and Series palette below still layer their own overrides on top of whichever theme is active.

Header background color: further down, below Accent color, the Header background color picker sets a flat fill for the banner itself (the default is a navy gradient) — text color auto-adjusts for contrast (dark text on a light pick, white on a dark one), so it's always readable. This is separate from Accent color, which only tints the bottom border plus chart/button accents throughout the dashboard. Click "Reset to default" to go back to the standard navy banner.

Edit JSON spec (power users): the Edit JSON spec… command palette entry (⌘K / Ctrl K) opens the whole working dashboard as raw, editable JSON in a text box — Views, KPIs, filters, style, everything. Useful for bulk edits, scripting a change outside the app and pasting it back in, or just seeing exactly what the builder is tracking. Apply validates it's well-formed JSON with the shape a spec needs (a widgets array and a cda.dataAccesses array) before applying — an invalid edit shows an inline error and changes nothing. A checkpoint of the dashboard as it stood right before your edit is saved to Version history first, so any hand-edit is always one restore away from being undone.

Build progress: the top of the dashboard inspector shows a small ring + checklist tracking five well-rounded-dashboard milestones — a real title, a View, a KPI, a filter, and a touch of your own style (accent color, series palette, or header logo). It's purely encouraging, not a warning — an empty dashboard is perfectly valid — and disappears into a one-line "nice work" note once every milestone is met. Distinct from the Checks section right below it, which only flags real problems (missing data bindings, an invalid file-name stem, etc) — including a note when a data access is declared but not actually used by any View or KPI, so leftover config from an earlier draft doesn't go unnoticed. All six direct-query connectors (DuckDB, SQLite, Snowflake, Databricks, BigQuery, Generic SQL/HTTP) now have a real live-query runtime once a dashboard is actually exported/deployed, so none of them trigger a Checks warning anymore. The first time a given dashboard reaches genuinely zero Checks issues, it gets a small one-time celebration (toast + spark burst) — the same delight moment a first export or an export milestone gets. Collapse the Checks section and its header shows a glanceable summary too — "all clear," or a count like "1 error, 2 warnings" — so you don't have to reopen it just to see whether anything needs attention.

Drag and drop

  • Drag a DA card from the library → drop on the canvas to add a chart View.
  • Drag a View's header grip → drop between any other Views to reorder (across rows).

Ensembles & scientific honesty

When several sources estimate the same thing — several vendors' models, several surveys, several labs — the Ensemble chart and the Map (US choropleth) chart are built around one rule: the common estimate is the product, not a leaderboard. The sections below explain the design choices behind that rule and how to read (or build) an honest ensemble dashboard.

The median is bold; providers are supporting evidence

On both charts, the combined value — the median of whichever sources are currently toggled on — always renders as the boldest, most prominent element: a thick line on Ensemble, the fill color on the map. Individual providers draw thin and muted (hollow dots, low opacity) — present so you can inspect the underlying evidence, but never competing visually with the estimate itself. Toggling a provider off (click its chip under an Ensemble chart) removes it from the median calculation everywhere it's used, including any map sharing the same ensemble channel (the map's Provider/series column option) — both charts recompute and re-render live from the same reduced set.

The agreement band is a confidence signal, not decoration

The translucent band around the Ensemble chart's median line spans the full range of the toggled-on providers at each point. Read it literally: a tight band means the sources agree (high confidence in the estimate there), and a wide band means they don't (treat that point with more caution). It is not a stylistic flourish — it's the chart's way of showing uncertainty honestly instead of hiding it behind a single confident-looking line.

A reference series is context, never the estimate

Both charts support an optional reference series (e.g. an independent census or ground-truth figure) drawn as hollow markers, visually distinct from the provider lines and the median. A reference series is deliberately excluded from the median calculation — it's there to let a viewer compare the ensemble's estimate against an outside benchmark, not to be folded into the estimate itself.

No-data is shown, never guessed

The choropleth renders regions with no data as a hatched "No data" texture rather than leaving them blank (easy to misread as zero) or interpolating a value (which would misrepresent coverage). Combined with the provenance popover below, a viewer always knows exactly how much of the map is real data versus gaps.

Checking the honesty story: the ⓘ Sources popover

Both charts have an ⓘ Sources button next to their legend that opens a popover answering "how much of this can I trust?": on the map, what fraction of regions actually carry data (and, when a provider column is mapped, each provider's own region count); on the Ensemble chart, how many providers are currently selected, how many points have every selected provider reporting (full coverage — a stricter, more honest signal than the agreement band alone), each provider's own point count, and the reference series' point count with a reminder that it never joins the estimate. When the chart's data comes from a saved workspace dataset, the popover also shows a Last updated line — the dataset's own timestamp, which a re-run prep job bumps automatically, so a chart is honest about its own freshness and not just its providers. The popover stays open while you read it (unlike a hover tooltip) and works identically in an exported dashboard.

Handing off the underlying numbers

Both charts' Download data button (the same on-canvas control every View has — see "Downloading a View's image or data" below) exports exactly the selection currently shown — the map's region id/value pairs post-aggregation, or the Ensemble chart's long-format label/provider/value rows for the toggled-on providers plus the computed median and any reference series — instead of the raw bound query. Re-download after toggling a provider and the file reflects the new selection — a quick way to hand a stakeholder the same numbers the chart is drawing from.

Browser-native connectors: no backend required

Two source types query a file hosted anywhere over plain HTTP — S3, any static host — entirely inside your browser, with no proxy, no saved credentials, and no server connection. Both intercept the query engine's disk reads and turn them into HTTP Range Requests, so they only transfer the bytes a query actually touches. Both are flagged with a small "Browser-only" badge on their source-type card in the New Source builder, and a failed Test connection surfaces a plain-English hint (CORS/Range support, a slow/unreachable host, a 404) instead of a raw browser error. Pick whichever fits your workload:

  • DuckDB (remote file) is the columnar / analytics engine — best for aggregations and dashboards over a Parquet or CSV file, via DuckDB-Wasm.
  • SQLite (remote .sqlite) is the relational / indexed-lookup engine — best for point lookups and small joins over a .sqlite file with real indexes, via sql.js-httpvfs. An indexed query only fetches the handful of ~4KB pages it needs, even from a multi-GB file.

DuckDB (remote file):

  • Set the File URL (and optionally the format — auto-detected from the extension) and click Test connection & detect columns. This lazy-loads the ~3–5MB DuckDB engine the first time it's needed, registers the file, and runs a schema probe — the base app stays small until you actually use this connector.
  • The optional Query field runs SQL against the file, aliased as the view t (e.g. SELECT region, SUM(revenue) FROM t GROUP BY region). Leave it blank for SELECT * FROM t LIMIT 200.
  • The Data preview's Run live button queries the real file the same way — no server required.

SQLite (remote .sqlite):

  • Set the File URL and optionally a Table name, then click Test connection & detect columns. Leave the table blank and Studio auto-picks the first table in the file; the test lists its columns via PRAGMA table_info and a 5-row sample.
  • The optional Query field runs SQL against the opened database (any table in the file, not just the detected one). Leave it blank for SELECT * FROM <table> LIMIT 200.
  • The Data preview's Run live button queries the real file the same way — no server required.

Both connectors run genuinely live everywhere: the builder itself (Test connection, Run live, the live-preview iframe), the offline sample preview used while you're building, and — a downloaded/deployed dashboard .html export queries the real file directly too, no server involved (the export bundles the small connector façade automatically whenever a dashboard uses one).

Snowflake connector

The Snowflake source type queries a live warehouse directly from the browser via Snowflake's SQL API — no backend or proxy, but unlike the file connectors above it's credential-based and flagged with a "Needs token" badge instead of "Browser-only". Two things to set up before it will work:

  • A token, never a password. Generate a Programmatic Access Token (or use an OAuth access token) in Snowflake and paste it into Access token; pick the matching Token type. Studio never asks for or stores a Snowflake username/password.
  • CORS allow-listing. Snowflake blocks cross-origin browser calls by default — a Snowflake admin must add this app's origin to the account's ALLOWED_HTTP_ORIGINS network policy before Test connection will succeed. Until then, requests fail with a clear CORS hint rather than a stuck spinner.

Fill in Account identifier (e.g. xy12345.us-east-1), Warehouse/Database/Schema and an optional Role, write a Query, then click Test connection & detect columns — it runs SELECT 1 to validate everything and, once you have a real query, detects output columns from the live result. The Data preview's Run live button queries the warehouse the same way.

Databricks connector

The Databricks source type queries a live SQL warehouse directly from the browser via Databricks' Statement Execution API — no backend or proxy, same credential-based shape as the Snowflake connector above and flagged with the same "Needs token" badge. Two things to set up before it will work:

  • A personal access token, never a password. Generate one under Databricks' Settings → Developer → Access tokens and paste it into Access token. Studio never asks for or stores a Databricks username/password.
  • An allowed origin. Databricks workspaces don't emit permissive CORS headers by default — check with your workspace admin that this app's origin is allowed, or requests will fail on CORS with a clear inline hint rather than a stuck spinner.

Fill in the Workspace host (e.g. dbc-a1b2c3d4-e5f6.cloud.databricks.com, no protocol), the SQL warehouse id (from the warehouse's Connection details), and optionally a Catalog/Schema, write a Query, then click Test connection & detect columns — it runs SELECT 1 to validate everything and, once you have a real query, detects output columns from the live result. The Data preview's Run live button queries the warehouse the same way; statements that start out PENDING/RUNNING are polled automatically.

BigQuery connector

The BigQuery source type queries a live dataset directly from the browser via Google's jobs.query REST API — no backend or proxy. It's credential-based like Snowflake/Databricks above, flagged with the same "Needs token" badge, but Google's API already sends permissive CORS headers for this endpoint, so there's no admin allow-listing step — the token itself is the only gate.

  • A short-lived OAuth 2.0 access token, never a service-account key file. Paste it into Access token; Studio never asks for or stores a downloadable key.

Fill in the Project id (e.g. my-analytics-project) and optionally a job Location (e.g. US, needed for datasets outside the default region) and a Default dataset (so unqualified table names resolve against it), write a Query, then click Test connection & detect columns — it runs SELECT 1 to validate the project/token and, once you have a real query, detects output columns from the live result. The Data preview's Run live button queries the dataset the same way; jobs that don't complete immediately are polled automatically.

Generic SQL/HTTP connector

The Generic SQL/HTTP source type is the escape hatch: it POSTs (or GETs) a SQL string to any JSON API you point it at — an in-house query service, a serverless function, or a provider not yet covered by a named connector — straight from the browser, no backend or proxy. Flagged with a "Needs endpoint" badge (not "Needs token" — auth is optional and entirely up to your endpoint).

  • Fill in the Endpoint URL, pick a Method (POST sends a JSON body, GET appends a query-string param), and optionally an Auth header (the full header value, e.g. Bearer … — sent as-is, nothing is stored beyond your browser).
  • Param name (default sql) is the JSON key or query-string key that carries the query text — match it to whatever your endpoint expects.
  • Write a Query, then click Test connection & detect columns — it sends SELECT 1 and detects output columns from the live response. The Data preview's Run live button queries the endpoint the same way.
  • The response can be shaped three ways: an array of row objects ([{"col":1,...}]), the same nested under {"data":[...]}, or an already column/row-shaped {"columns":[...],"rows":[[...]]}.

Live after export, credentials prompted at open: like DuckDB/SQLite, all four credential-based connectors above (Snowflake, Databricks, BigQuery, Generic SQL/HTTP) now query live once a Dashboard Framework .html is downloaded/deployed too — but unlike the file connectors, they need a real secret (an access token or auth header), and that secret is never baked into the exported file. Export strips it out of the DA before the file is written; the first time an exported dashboard actually needs to run one of these queries, it prompts once for just that value (a plain browser prompt naming the connector and the data access) and keeps it in memory only for the rest of that page load — never written to disk, localStorage, or the file itself. Every other field (account, host, project, warehouse, etc.) still travels with the export as before, since none of those are secrets on their own.

Workspace connections: PostgreSQL (PostgREST)

The Connections section (left rail) manages saved, credentialed connections that workspace Datasets query through. Every password-style field you type a credential into — on the sign-in screen, here, in the workspace-backend wizard, on Admin's Add-user form, and on the per-user-security provision-secret prompt — has a small eye toggle next to it to reveal or re-hide what you typed, so you can double-check it before saving. Alongside the workspace backends (Turso, Supabase, Firebase) and the warehouse connectors above, the PostgreSQL (PostgREST) adapter connects to any Postgres exposed through a PostgREST deployment — self-hosted or managed — straight from the browser. Set the PostgREST URL (its root answers with the OpenAPI document, which is exactly what Test checks), an optional Bearer token (a PostgREST JWT; leave blank for anonymous access), and an optional Schema (sent as Accept-Profile for multi-schema deployments). Datasets on this connection are table-based, like Supabase: a table or view name plus an optional raw PostgREST query string (select=region,total&order=total.desc&limit=200) — with {{parameters}} allowed in both, so dashboard template variables flow into filters like region=eq.{{region}} at run time.

Connection-bound datasets — Turso, PostgreSQL (PostgREST), Supabase, Google Sheets, local files and Amazon Redshift: a dataset built on a saved Connection (rather than one of the direct connectors above) is now live-after-export too, for all six connection-bound backends. Exporting resolves the dataset's connection at export time, carries its non-secret fields (e.g. the database URL, PostgREST's URL/schema, the sheet's URL, or Redshift's region/database/cluster/workgroup) into the file, and — same "prompted once, never embedded" contract as the direct connectors — strips the credential, prompting for it the first time the exported dashboard actually needs to query live (a PostgREST connection with no token set, i.e. anonymous access, and a link-shared Google Sheets connection with no OAuth token set, need no prompt at all — and neither does a dropped file, which has no credential in the first place). A dropped file needs no live query at all: its content already rides inside the export, exactly as it does in the builder. Redshift is the one exception to "one prompt": since AWS SigV4 signing needs an access key ID and secret access key (plus an optional session token for temporary credentials), the exported dashboard prompts once per credential field instead of once overall.

Signing in with real Supabase Auth (optional)

The Supabase backend's connect wizard has two extra, optional fields below the Project URL and anon key: Supabase Auth email and password. Leave them blank and Supabase behaves exactly as before — every request uses the shared anon key. Fill them in and Studio signs in with real Supabase Auth (GoTrue) first, then sends that session's JWT on every request instead — so Postgres' auth.uid() resolves to your real account rather than staying NULL. This is groundwork for enforced, database-level per-user privacy on top of the private/public flags every object already carries (Dashboards, Datasets, Connections, Jobs, Analyses) — those flags are UX-level today (hidden from other accounts in the UI); a real Supabase Auth sign-in is the prerequisite for the database itself to enforce it via Row-Level Security. A wrong password fails clearly at the "Check database →" step, the same gate that already validates the URL and anon key, so it can't silently connect with the wrong identity.

Adding users when connected to Supabase (in-app account provisioning)

Once the workspace backend is Supabase, the Admin page's + Add user form gains an Email field and does one extra step: it creates a real Supabase Auth (GoTrue) account for the new user via Supabase's public sign-up endpoint, then stamps the resulting account id onto their row — no Supabase dashboard visit, and no admin/service-key credential ever handled in the browser. This means an admin can create and manage every account entirely from Polecat's own Admin console; only the very first admin account needs a one-time bootstrap in Supabase itself. Editing an existing user never repeats this step. Two things can leave the new account temporarily unusable, and the form explains each clearly rather than failing silently: the Supabase project has sign-ups turned off (Authentication → Providers → Email), or it still requires email confirmation before an account can sign in — turn off "Confirm email" in the same settings page, then add the user again.

Per-user provisioning defaults (first sign-in)

The Admin page's Add user (and Edit user) form has a Default theme picker and an "Install the Conservation Insight sample pack on first sign-in" checkbox. Set either and that new account logs in ready: the app color theme switches to the one you picked and, if checked, the Conservation Insight sample pack installs itself — no manual setup, no digging through Settings. This only ever runs once, the very first time the account signs in anywhere; after that it's stamped as provisioned and later logins never fight whatever the user has since changed for themselves. Leaving the theme at "Don't set" or the pack box unchecked simply skips that part.

The same form also has a "Copy my current Dashboard defaults" button — click it and Studio snapshots every field from your own Settings → Dashboard defaults card (default subtitle, accent color, header logo, header background, title size, subtitle style, dashboard theme, card style, and Quick-import creativity) and stashes it on the new account. At their first sign-in, that whole "house style" applies automatically alongside the theme/pack above, same once-only rule. Clear removes a previously captured snapshot before saving.

Managing multiple backends (admin)

The Admin page's Backends card lets an admin pre-register more than one backend — Turso, Supabase, or Firebase — under a name, with its own credentials, ahead of actually connecting to any of them. Click + Add backend, pick the adapter, and fill in its fields (the same ones the connect wizard uses); Test checks the credentials without connecting. Each registered backend gets its own Edit/Test/delete controls, and a Connect button that runs the exact same connect flow as Settings → Workspace backend, so nothing about probing or adopting an existing workspace changes — only the currently-connected one is ever active, shown with an active badge. Registering a backend here is just remembering its name and credentials for later; it does not sync, mirror, or connect anything by itself. A registered backend with users assigned to it (below) shows a count badge, e.g. "2 users". Once at least one is registered, Settings → Workspace backend's Switch backend button offers this same list first — pick one to connect in a click, or "Enter connection details manually" to start a brand-new connection from scratch.

Once at least one backend is registered, the Add/Edit user form (same "Per-user provisioning defaults" area above) also gains an Assigned backend picker naming which registered backend that account belongs to — shown back on their row in the Users list too (→ Backend name). This is reference metadata for now, not an automatic connection: assigning a backend doesn't make a device connect to it, since adopting a backend can replace that device's entire local workspace, which shouldn't happen silently. A consolidated config UI (or a future "select a server" step) is the next slice to act on the assignment.

Going live with real per-user security (Supabase)

The private/public flag on every object (Dashboards, Datasets, Connections, Jobs, Analyses) is UX-level by default — a private object is hidden from other accounts in the app, but the connected Supabase backend still stores everything under one shared key. An admin can flip that to real database-enforced Row-Level Security from the Admin page's "Enable per-user security / Go live" card, once a small one-time relay — the polecat-admin Supabase Edge Function — has been deployed (see tools/M7-RLS-GOLIVE-RUNBOOK.md for the exact deploy commands; it's a repo maintainer's one-time step, not something the app can do for you). Once deployed, paste its URL into the Supabase connection's Admin function URL field, sign in as the account that should become the first admin (the Auth email/password fields above), then click Go live and enter the one-time provision secret set when the function was deployed — it's used once and never stored. Go live wipes the current workspace tables (your browser's own data is untouched), seeds you as the admin, and applies the real per-user policies; from then on, private truly means only you (and admins) can see it, enforced by the database itself. With the relay deployed, + Add user also switches to it automatically for the more secure admin-create path (no email-confirmation step) — the plain self-signup described above remains the fallback wherever the relay isn't deployed.

First-admin bootstrap is automatic. Go live records your own admin account for you (in the database) before it runs, so on a brand-new project it no longer stops with "This account is not an admin of this workspace" — you don't have to hand-run any SQL in the Supabase editor to make yourself the first admin. It also refreshes your Supabase Auth sign-in each time, so a session that quietly expired won't surface as "That sign-in session is no longer valid" — just click Go live (or + Add user) again. The one prerequisite the app still can't do for you is the maintainer's one-time polecat-admin function deploy above.

Workspace connections: Amazon Redshift

The Amazon Redshift adapter queries a provisioned cluster or a Serverless workgroup directly from the browser via the Redshift Data API — no backend or proxy. Unlike the warehouse connectors above (Snowflake/Databricks/BigQuery), Redshift's API has no bearer-token mode: every request is individually signed with an AWS Signature Version 4 — set an Access key ID, Secret access key and, for temporary/STS credentials, a Session token. Set the AWS region and Database, then target either a provisioned cluster (Cluster identifier + Database user, using temporary credentials — no stored DB password) or a Serverless workgroup (Workgroup name alone); an optional Custom endpoint supports a VPC PrivateLink deployment. Statement execution is asynchronous (fire, then poll) the same way Databricks' Statement Execution API works — Studio handles the polling and result pagination automatically.

Browse a connection's schema

For Snowflake, Databricks, BigQuery, Amazon Redshift, PostgreSQL (PostgREST), DuckDB and SQLite connections, the Connections editor gains a Browse schema button next to Test connection — click it (after filling in credentials) to list every table the connection can see, each expandable to show its columns and types. A filter box narrows a long table list by name. This reads live metadata only — an information_schema.columns query for the SQL warehouses (BigQuery's own INFORMATION_SCHEMA.COLUMNS queries unqualified when the connection has a default dataset set, or a project-and-region-qualified view across every dataset in that region otherwise), PostgREST's own OpenAPI document (the same one Test connection already checks for), a DESCRIBE of the registered file for DuckDB (a connection is always exactly one file, so the "tree" is a single table named after it), or sqlite_master + PRAGMA table_info per table for SQLite — it never changes anything. Generic SQL/HTTP doesn't show the button: it's an arbitrary JSON API with no reliable dialect or catalog to introspect.

Workspace connections: Google Sheets

The Google Sheets adapter charts a sheet shared as "anyone with the link can view" straight from the browser — no OAuth, no API key. Paste the sheet's URL (or just its id) into the connection; datasets on it pick an optional Tab (the first tab when blank) and an optional Query in Google's query language — columns are addressed as A, B, C…, e.g. select A, sum(B) group by A — with {{parameters}} allowed, so dashboard template variables flow into clauses like where A = '{{region}}' at run time. Header labels become column names, dates render in their formatted form, and a private sheet gets a friendly "share the link" hint instead of a raw error.

For a private sheet, fill in the connection's optional OAuth access token field — a short-lived Google OAuth 2.0 access token scoped to spreadsheets.readonly (e.g. from the OAuth Playground), the same "paste a token, never a key file" shape as the BigQuery connector. When a token is set, the connection queries the Sheets API v4 instead of the public gviz endpoint: the chosen Tab reads as a plain values range (header row → column names, the rest → data rows) — the gviz query language above doesn't exist in v4, so a private-sheet dataset can't filter/sort server-side yet; leave the token blank to keep using tq queries against a link-shared sheet. An expired or scope-mismatched token surfaces a clear message instead of a raw 401/403.

Workspace connections: CSV / JSON files

The CSV / JSON file adapter is the fastest way from a file on your disk to a chart: add a file connection (nothing to configure), create a dataset on it, and drop a .csv, .tsv or .json file onto the editor's drop zone (or click it to browse). The file's data is stored inside the dataset — it works fully offline, needs no re-picking after a reload, and travels with your workspace (including to a remote backend). CSVs handle quoted fields and sniff comma/semicolon/tab delimiters; numeric cells become real numbers so charts can aggregate them; JSON expects an array of row objects. Files are capped at ~2MB — bigger data belongs in the DuckDB (remote file) connector, which streams only the bytes a query touches.

Calculated columns

Every data source has a Calculated columns section (Advanced mode) for formula-based columns derived from its own output columns — e.g. =[revenue]-[cost] for a margin, =[revenue]/1000 to rescale a value, =pctChange([revenue]) for the percent change vs. the previous row (in percentage points, e.g. 12.5 for +12.5%; the first row has no prior row to compare against, so it's blank there), or =movingAvg([revenue], 5) for a trailing 5-row average (defaults to 3; partial windows at the very start average whatever's available, the same convention as the line chart's own Show moving average overlay). Give it a Name and a Formula referencing other output columns in square brackets; the four arithmetic operators and parentheses are also supported (+ - * / ( )). A bad reference (an unknown column, a divide-by-zero, malformed syntax) shows a small inline error naming the problem rather than silently failing. Once valid, the calculated column is a real, bindable column everywhere a View/KPI picks a column from this data source, and its value is computed live in the offline sample preview. For all six direct-query connectors (DuckDB, SQLite, Snowflake, Databricks, BigQuery, Generic SQL/HTTP), a calculated column is also appended to the live query result once the dashboard is exported/deployed — its value is computed the same way there as in the offline preview.

Data source freshness

Any data access with a Run live button (DuckDB, SQLite, Snowflake, Databricks, BigQuery, Generic SQL/HTTP, or a dataset bound to a workspace connection) shows a small "Last verified live …" / "Never verified live" badge next to it in the Data preview — stamped locally each time a live query actually succeeds, so a token that quietly expired or an endpoint that went dark doesn't get silently trusted just because it worked once. A successful Test connection & detect columns counts too, for the six direct connectors above — you don't have to run a full live query just to refresh the badge. The same badge appears on that data source's card in Dashboards and the library pane's My Data Sources section — but only for the connector kinds above, which are always live-capable on their own; a plain sample-engine SQL data source stays badge-free instead of showing "Never verified live" everywhere.

Joins and compound DAs

Click ⧈ Join in the library to create a Compound data access — either a join (left/right DA + key columns) or a union (stack rows from N DAs). The result is computed in the builder over the member DAs' rows.

Dataset lineage

The Datasets catalog badges each row with "↪ N dashboards" when one or more saved dashboards reference it — hover the badge for the list of names. It's a blast-radius view: before deleting a dataset, you can see what depends on it. Deleting one that's in use warns you which dashboards reference it — they don't break, but they fall back to the self-contained copy of the query that was saved into them the last time they linked to it, rather than continuing to follow live edits to the dataset.

Filtering datasets and connections

The Datasets list can be narrowed by four cross-cutting pill strips at once — by adapter (every Postgres/Snowflake/file/etc. connection grouped together), by one specific connection (e.g. just "Prod DB" out of several Postgres connections), by type (SQL query / Table / Collection / File / Sheet — what kind of definition the dataset holds), and by tag — plus the search box. Click a pill to toggle it on; multiple pills in the same strip are OR'd together, different strips are AND'd. The Connections list has the same by-adapter and by-tag pills (give a connection Tags — a comma-separated list, editable in its wizard — to slice a growing catalog by e.g. "prod" vs. "staging" without adding a new connection per environment). A "Clear" chip resets every filter at once.

Filing a dataset, connection, job or analysis into a Folder

A dataset's editor, a connection's wizard, a job's editor, Explore's savebar (next to the analysis name), and — via the Repository quick-edit panel — a dashboard all have a Folder field — a home for it (e.g. "Finance"), distinct from Tags (which can be many). Type a new name or pick an existing one from the suggestions, or click the Browse button next to the field to navigate a proper folder-tree picker instead — breadcrumb into an existing folder, search across every filed path, or create a new (even nested) one inline, then pick or "Use" it to fill the field; every Folder field, including Explore's, has this Browse button. Type Parent/Child (e.g. "Finance/2024") to nest it under a parent folder in the Repository tree below — that "/" only affects how Repository groups the item, everywhere else it's still matched as one whole folder name. Once at least one item has been filed, the Datasets, Connections, Jobs, or Explore's saved-analyses list shows a folder chip strip (All folders / each folder / Unfiled) above the other filters (Jobs also gains a search box alongside it), and a small badge on the row names its folder.

Repository — search the whole workspace

The Repository section (left rail, after Connections) is a single searchable view of every object in your workspace — dashboards, datasets, connections, analyses, and jobs — with a chip strip to narrow to just one kind and a running count on each. Rows are organized into a real nested folder TREE: a "/" in a folder name (e.g. "Finance/2024") becomes a parent folder containing a collapsible child folder, and a folder's header shows the total count of everything inside it, subfolders included. Folders sort A→Z at each level; a root-level "Unfiled" group for anything with no folder always comes last. All five kinds — Dashboards, Datasets, Connections, Jobs and Analyses — carry a folder today. Click any folder's header to collapse or expand just that branch. A row shows that object's folder badge when it has one and when it was last touched; opening a row takes you straight into that object's own editor rather than duplicating one here — a dataset or connection opens its edit modal, a job opens its editor, and a dashboard or analysis switches you into Studio or Explore with it loaded. It's the fastest way to find one specific thing once a workspace has grown past a glance. A small pencil button on any row (hover or focus to reveal it) opens a quick edit panel to rename it (dashboards keep their title in Studio's own settings, so this one is folder-only) or change its folder right there, with an "Open full editor →" link if you need the real editor. A + New folder box (shown while browsing with no search or type filter active) lets you create an empty folder — even a nested one, e.g. "Finance/2024" — ahead of filing anything into it; an empty folder you created this way shows a small ✕ on hover to remove it again (harmless: it only removes the placeholder, never any rows), which disappears once something real is actually filed there. On a mouse, you can also just drag a row onto a folder's header to refile it there instantly (drag onto Unfiled to clear its folder); typing a folder name is still the primary, fully mobile-capable way to file something, so drag is purely a desktop shortcut on top of it. A Tile view button next to the search box switches every folder group from the compact list to a richer tile grid (same toggle as Dashboards, Datasets, Connections and Jobs) — your choice is remembered per device.

Saved views

Once a search and/or adapter/connection/type/tag pill selection narrows the Datasets or Connections list to something worth returning to, a "+ Save view" box appears next to the filter chips — name it and it becomes a chip of its own. Click that chip later to instantly restore the exact same search text and filters; hover it for a small trash button to delete it. Saved views live in the same workspace-settings store as Dashboards' workbooks, so they sync across devices along with the rest of your workspace.

Marking a dashboard, connection, dataset, analysis, or job private

A lock toggle on every Dashboards, Connections, Datasets, and Jobs row, and every saved analysis in Explore's list marks that item private — it stays visible to you and to admin accounts, but disappears from every other signed-in account's catalogs (and, for connections, from the connection picker other people see when authoring a dataset, and for datasets, from the source/join/union dataset pickers when authoring a job). This is UX-level gating, the same honesty as the rest of sign-in — an admin account (or local/no-auth mode with no sign-in configured) always sees everything. All five saved-object types now have the toggle.

Saving and loading your work

  • Save (Ctrl S / ⌘ S) — saves the dashboard to your Dashboards catalog (and cuts a version-history checkpoint). To get a file instead, use Export ▾ → Editable spec (.studio.json) — that file is all a dashboard needs.
  • Save as… — saves the current dashboard as a brand-new one (you name it) instead of overwriting the one you opened. Sample/demo content is always read-only: hitting plain Save on a sample dashboard automatically opens the Save-as prompt instead of silently overwriting it, so removing or reinstalling a sample pack never clobbers your edits — they live on in your own copy.
  • Open — picks a dashboard from your catalog; its footer also offers Open file… (accepts .studio.json or a previously exported .html — Studio embeds the spec in exported files) and Import from URL….

Dashboard defaults

The Settings page has a Dashboard defaults card with a Default subtitle field, a Default accent color picker (the same swatches as the per-dashboard Accent color field), a Default header logo upload, a Default header background color picker (same flat-fill banner field as the per-dashboard Header background color setting; blank keeps the standard navy gradient), matching Default title size / Default subtitle style pickers, and a Default dashboard theme picker (same whole-look Classic Blue / Polecat / Fleet Modern / High Contrast / Editorial / Neon / Conservation choice as the per-dashboard Dashboard theme field; left unset, it follows whichever app Color theme is active — Polecat app theme → Polecat, Classic Blue → Classic Blue, Fleet Modern → Fleet Modern — until you pick an explicit default here). All seven are applied automatically to every brand-new Blank dashboard (Home's quick-create card or New ▾ → Blank dashboard) — handy for teams with a house tagline, brand color, logo, banner fill, text formatting, or whole-look theme. Existing dashboards, examples, and imports are never touched. Carried along by Export/Import settings and included in Clear local data.

Below that, Style presets lets you save the current set of defaults above as a named preset — type a name and click "+ Save as preset". Save more than one (e.g. one per client) and click Apply on any saved preset to switch which one is the active default; the trash button removes a preset. A preset with a saved logo shows a small thumbnail instead of a plain color swatch. Presets travel with Export/Import settings and are included in Clear local data too.

Backing up your settings

The Settings page has a Data card with Export settings / Import settings. This saves/restores your theme, mode, workspace connections, and pane-layout preferences as a .json file — handy before clearing local data, or to carry your setup to another browser or device. It only covers app preferences, not dashboard content (use Save / Open for a .studio.json).

Branding & app identity

The Admin section has a Branding & app identity card — it's app-wide (what everyone who opens the workspace sees), so only admins can change it. It controls three things:

  • App mark — the icon at the top of the left rail: Default (the Analytics mark), Custom logo, or None. A custom logo should be a square PNG/JPG/SVG (ideally a simple, transparent-background icon around 64–256 px, up to 200 KB) — it renders small in the rail and tiny in the browser tab, so avoid fine detail or lots of text.
  • Favicon — when you set a custom logo it also becomes the browser-tab favicon, so a white-labeled app matches in the tab.
  • Suite name — the small label under the app name in the rail (polecat.live by default). Set your own short white-label name (up to 24 characters — keep it to a word or two so the rail lockup stays tidy) or hide it entirely.

Branding is stored locally on this device as part of your Settings, so Export settings carries it along. This only affects the app's own chrome — it's independent of any exported dashboard's branding.

Color theme

The Appearance card on the Settings page has a Color theme picker, separate from the Dark mode switch — clickable palette cards, not a dropdown, each showing a small preview banner and color dots of its OWN actual chrome colors so you pick by looking rather than reading a label. The picker now offers the same seven looks as the Dashboard theme picker, so the app chrome and a dashboard can read as one system: Polecat (the warm terracotta/plum/cream house palette — the default), Classic Blue (the original built-in chrome), Fleet Modern (the cooler jobtracker.polecat.live palette), High Contrast (stark black/white with solid borders for maximum legibility), Editorial (a warm paper-and-ink boardroom mood), Neon (a synthwave near-black chrome with electric cyan/magenta accents), and Conservation (the CTIC olive/field-green and deep-pine look — built for the Conservation Insight demo, but usable as the whole app's look any time). Each is shared verbatim with the matching dashboard theme. The active card shows a checkmark. Each theme has its own light and dark variant, so it combines freely with the Dark mode toggle. Picking an app Color theme also sets the default Dashboard theme a brand-new dashboard seeds from (unless you've picked an explicit Default dashboard theme in Settings), so a Conservation app + a Conservation dashboard stay in lockstep with one click. Carried along by Export/Import settings. Exported dashboards are unaffected — their theming stays independent of the app's own chrome.
